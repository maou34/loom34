## Commands

```bash
npm run dev              # Vite dev server on :8080 (proxies /upload to the upload server on :8081)
npm run build             # Production build
npm run build:dev         # Development-mode build
npm run lint               # ESLint
npm run preview            # Serve the production build on :4173

npm run server:upload      # Runs the separate Express image-upload server (server/upload.js), :8081

npm run migrate:gallery    # One-off script: migrates images from Supabase Storage to public/gallery
npm run compress:gallery   # Re-compresses images already in public/gallery (resize + re-encode); dry-run by default, `-- --write` to apply
npm run pull:gallery        # Downloads every image from the upload server (prod by default) into public/gallery/ locally
npm run seo:generate        # Regenerates dist/sitemap.xml (runs automatically as `postbuild`)
npm run seo:validate        # Validates SEO output (scripts/validate-seo.js)
node scripts/site-check.mjs   # Renders every sitemap page in headless Chrome against prod: 404s, JS errors, broken images/links, certificates (~6 min)
node scripts/audit-deps.mjs   # npm audit (production deps) with an explicit ACCEPTED list; exits 1 on anything unaccepted ≥ moderate
```

There is no test suite configured in this repo. A weekly GitHub Actions workflow (`.github/workflows/site-audit.yml`, Monday 5:30 UTC + manual run) runs those two scripts plus Lighthouse CI (`lighthouserc.json`: accessibility ≥ 95, best practices ≥ 90, SEO ≥ 90 blocking; performance ≥ 25 warning only — the site is at ~30 on mobile) against the live site; a failed job e-mails the repo owner. The repo is public: step summaries are public too. Dependabot (`.github/dependabot.yml`) opens one grouped PR per month. When accepting a vulnerability instead of fixing it, add its GHSA id to `ACCEPTED` in `scripts/audit-deps.mjs` with a reason and a review date.

## Architecture

React 18 + TypeScript SPA built with Vite, Tailwind + shadcn/ui (Radix), React Router v6, and TanStack Query. Supabase (Postgres + Auth) is the backend; there is no custom API server for app data.

### Data layer: three different Supabase surfaces exist

- **`@/db/client`** (`db`) — the client actually used almost everywhere, typed against `src/db/types.ts` (hand-maintained `Database` type, kept in sync manually — see below).
- **`@/lib/supabaseClient`** (`supabase`) — a second, untyped client instance, used only by `pages/auth/ResetPasswordRequest.tsx` and `pages/auth/UpdatePassword.tsx`.
- **`@/integrations/supabase/types.ts`** — a separate, likely stale copy of the `Database` type (no client of its own), used only for type annotations in the gallery admin components and `EditUserForm.tsx`.

When adding a table/column, update `src/db/types.ts` — the one `@/db/client` actually uses — and check whether `src/integrations/supabase/types.ts` needs the same change if the file you're touching imports types from there.

### Schema changes have no migration tooling

There's a `supabase/` directory (CLI config, edge functions) but no `supabase/migrations/`. Tables are created by hand in the Supabase SQL Editor. Each table has a matching `.sql` file in `src/db/` (e.g. `contact_tickets.sql`, `site_settings.sql`) that documents its schema — these are **not** auto-applied; changes must be pasted into the Supabase dashboard's SQL Editor manually, and `src/db/types.ts` updated to match by hand. Until Nov 2026 RLS was actually **disabled** on `events`, `articles`, `gallery_albums`, `gallery_images`, `partners` and `contact_tickets` while `anon` held INSERT/UPDATE/DELETE on them (existing policies were written but inert); `src/db/rls_lockdown.sql` adds explicit admin policies, enables RLS and revokes anon's write grants (anon keeps only INSERT on `contact_tickets` for the contact form). When debugging « policy has no effect », check `pg_class.relrowsecurity` first. `src/db/profiles_lockdown.sql` (applied 18/11/2026) closed a privilege escalation: a permissive « update own profile » policy without WITH CHECK let any signed-up account set its own `profiles.is_admin` (exploited on 14/11/2026 by two `@ghostmail.dev` « Ghost Audit » accounts, now banned; public sign-ups are disabled in the Supabase dashboard since). A `protect_profile_is_admin` trigger now rejects any `is_admin` change coming through the API (`authenticator`) or sign-up (`supabase_auth_admin`) unless the caller is an admin or the service role; `profiles` rows are readable only by their owner or an admin (`public.is_admin()` helper, SECURITY DEFINER to avoid policy recursion) — but `anon` must keep the SELECT *privilege* on `profiles` (RLS just returns no row): every admin/drafts policy elsewhere runs `EXISTS (SELECT … FROM profiles …)` even for visitors, and revoking it broke the public events/articles with « permission denied for table profiles » (18/11/2026, fixed the same day); `delete_user()` is admin-only and no longer executable by anon. Never add a permissive policy on `profiles` without thinking about `is_admin`. To ban an account by SQL, set `auth.users.banned_until` to a far-future date, never `'infinity'`: Postgres accepts it but Supabase Auth can't scan it, and `auth.admin.listUsers()` then fails for everyone with « Database error finding users ». `src/db/drafts_rls.sql` adds a RESTRICTIVE select policy on `events`/`articles` so unpublished rows are only readable by admins (before it, the anon key could read drafts); keep it in mind if a public page ever needs an unpublished row. New tables need RLS policies written explicitly (see `site_settings.sql` for the pattern: public `SELECT`, `INSERT`/`UPDATE`/`DELETE` gated on `profiles.is_admin`) — RLS is enabled by default and silently blocks writes (`42501` errors) if no policy is added. Separately, tables created in the SQL Editor don't automatically get SQL privileges for the API roles on this project: even `service_role` (which bypasses RLS) gets `permission denied for table …` until an explicit `GRANT … TO service_role` (and to `anon`/`authenticated` if the front needs it) is added — see `helloasso_ticketing.sql`.

### Auth & admin gating

`AuthContext` wraps Supabase Auth and exposes `isAuthenticated`/`isAdmin` (derived from `profiles.is_admin`) plus separate `isLoading` (session bootstrap) and `isProfileLoading` (profile fetch) flags. Routes are gated by nesting `<RequireAuth>` / `<RequireAdmin>` in `App.tsx` (see the `/admin/*` routes). `RequireAdmin` only blocks on `isProfileLoading` when there's no `profile` yet (`isProfileLoading && !profile`) — Supabase revalidates the session in the background whenever the tab regains focus, and gating on `isProfileLoading` unconditionally would remount the whole admin page (closing any open dialog) on every tab switch.

Admin accounts are managed only through the `admin-users` Edge Function (`supabase/functions/admin-users`, called via `callAdminUsers()` in `src/lib/adminUsers.ts`; `verify_jwt = false`, it checks the caller's session and `is_admin` itself): list (with e-mail/last sign-in from `auth.users`), invite by e-mail (Supabase `inviteUserByEmail`; an existing non-banned account is just promoted), revoke/restore `is_admin` (never yourself, never the last active admin), password reset e-mail, delete a non-admin account. E-mails go through the custom SMTP set in the Supabase dashboard (the association's Gmail); invite and reset links land on `/auth/update-password`, which must be listed in Authentication → URL Configuration → Redirect URLs. Public sign-up is closed (dashboard setting, and `/auth/register` now redirects to login). `admin-create-user` and the `delete_user` RPC are only kept for the front still on `main`; remove them once `new-ux-loom` is merged and deployed.

### Image/gallery storage is not Supabase Storage

The public Photos pages (`Gallery.tsx`, `AlbumDetail.tsx`) and the sitemap list albums and images from the upload server's API (`GET /upload/albums`, `/upload/albums/:id/images`), not from the DB — `gallery_albums`/`gallery_images` hold only leftover rows (still touched by the admin `Sortable*` components). Its write routes require an admin session token (see « Upload server auth » below). Images are static files served from `public/gallery/` by a standalone Express server (`server/upload.js`, run via `npm run server:upload`), not Supabase Storage. The DB (`gallery_images`, `gallery_albums`, plus `image`/`logo` columns elsewhere) only stores relative paths (e.g. `/gallery/<albumId>/file.jpg`); `src/config.ts` resolves `UPLOAD_URL` based on hostname (prod: `upload.lgbt-loom.fr`, dev: `localhost:8081`) and `getImageUrl()`/`ImageUpload.tsx` build the full URL. In dev, Vite proxies `/upload` to the upload server (see `vite.config.ts`). Uploaded files must be committed to `public/gallery/` to exist in production — there's no runtime persistence otherwise. `server/upload_SAV copy.js` is a stray backup file, not wired into any script.

**Upload server auth:** the write routes (`POST /upload[/]`, `POST /upload/albums`, `DELETE /upload/albums/:id`, `DELETE /upload/images`) go through `requireAdmin` (`server/auth.js`): the admin front sends its Supabase session token (`Authorization: Bearer …`, built by `uploadAuthHeaders()` in `src/lib/uploadAuth.ts` — use it for any new write call), the server checks it against `/auth/v1/user` and requires `profiles.is_admin` (results cached 1 min per token). GET routes stay public (the Photos pages use them). The server needs `SUPABASE_URL` + `SUPABASE_ANON_KEY` (or the `VITE_` ones; it loads `.env.local` / `.env` from its working directory on Node ≥ 20.12) — without them every write returns 503 rather than staying open. Before Nov 2026 these routes had no auth at all (CORS only, which doesn't stop curl). The server also only accepts real images (jpg/png/gif/webp: extension and MIME type in multer's filter, then the actual content checked with `detectImageFormat()` from `server/imageCompression.js` — the MIME type is client-supplied, and until Nov 2026 a text file renamed `x.jpg` was stored and served as-is from `upload.lgbt-loom.fr`), listens on `127.0.0.1` only (nginx proxies to it; `UPLOAD_HOST` to override — the Vite dev proxy targets `127.0.0.1:8081`), and answers errors as JSON. Those three hardenings were first written directly on the VPS (18/11/2026) and then brought into git: never edit files in `/var/www/loom34` by hand — it blocks the next `git pull`; and on the server never `git stash --include-untracked`, which would also stash the untracked `.env` the build and the upload server need. `components/admin/gallery/{AdminGallery,AlbumManager,DragDropGallery}.tsx` are not imported anywhere (legacy) and don't send the token.

Before sending, both upload paths (admin Galerie and `components/admin/ImageUpload.tsx`) pass each photo through `prepareImageForUpload()` (`src/lib/prepareImage.ts`): JPEG/HEIC are decoded in the browser (EXIF orientation applied), downscaled to 2400 px and re-encoded as JPEG; other formats get their bytes copied. Reason: from an iPhone, Safari's on-the-fly HEIC→JPEG conversion sometimes sent a truncated multipart body (busboy « Unexpected end of form », 21/11/2026) — keep it for any new upload call. The server answers that error with a 400 « Envoi interrompu » (and CORS rejections with 403) instead of a 500. Uploads are compressed server-side before being written to disk: `server/imageCompression.js` (resize to 2400px max on the longest side, `withoutEnlargement`, JPEG/WebP re-encoded at quality 82, PNG at max compression, EXIF orientation baked in via `.rotate()` then stripped) is shared by `server/upload.js` (new uploads) and `scripts/compress-gallery.js` (one-off retroactive pass over everything already in `public/gallery`, dry-run by default — `-- --write` to apply). `scripts/pull-gallery.js` is the counterpart for going the other way: it downloads every image from a running upload server (prod by default, override with `PULL_UPLOAD_URL`) into local `public/gallery/`, incrementally by default (skips files already present locally; `--force` re-downloads everything).

`.gitignore` only tracks `public/gallery/images/` (`public/gallery/*` is otherwise ignored) — that folder holds the site's own static assets (hero fallback, etc.) referenced by hardcoded paths, while per-album upload folders are meant to live only on the upload server's disk, not in the repo. That ignore rule was added late (Nov 2025) and doesn't retroactively untrack files committed before it existed — `public/gallery/unclassified/` had ~84 such files still in the git index despite being ignored, discovered when a bulk edit made them show up as modified. If a bulk script touches `public/gallery/` and unexpected album files show up in `git status`, check `git ls-files public/gallery` for stragglers like this and `git rm --cached` them rather than assuming the ignore rule is broken.

### HelloAsso ticketing (in progress, branch `feature/billetterie-helloasso`)

Paid events sell tickets through HelloAsso; decisions already made, don't revisit them without asking:

- **`events` is still the table the site reads, but HelloAsso is the source of truth for ticketed events.** An event has ticketing only if its optional `helloasso_form_slug` is set; events without one (apéros, etc.) behave exactly as before. `sync-events` **auto-imports** every upcoming HelloAsso Event form not yet linked (site slug = form slug, `-2`… on collision; fallback image `/loom_logo_square.jpg`), and on every sync **overwrites** title/date/time/location/description (HTML → Markdown via `htmlToMarkdown`)/image from HelloAsso — admin edits to those fields on a linked event are lost (the admin form warns about it). Publication follows `HELLOASSO_PUBLISH_MODE`: `draft` (default, **and LOOM's choice for prod too**) = imported unpublished, publication left to the site admin; `follow` = published iff the form is `Public` on HelloAsso. LOOM keeps its HelloAsso forms **Private** so people buy through the site (iframe/mobile bar use the direct link, which works for private forms — verified with a real sandbox payment), and the API reports both a private form and a draft as `state: "Private"`, so `follow` can't tell « private and ready » from « unfinished draft » — don't switch to it while forms are kept private. (Server-side `curl` on helloasso-sandbox.com pages returns 403 — that's HelloAsso's bot protection, not the private state.) **Sale period** (form `saleStartDate`/`saleEndDate`, only present when set on the HelloAsso form — `saleEndDate` verified in sandbox): synced into `helloasso_sale_start_date`/`helloasso_sale_end_date`. In `draft` mode, reaching `saleStartDate` publishes the event **once** (`helloasso_auto_published_at` records it, so an admin can unpublish afterwards; a changed `saleStartDate` re-arms it; no start date = stays draft until published by hand). Past `saleEndDate`, `getTicketAvailability()` returns `closed`: the event stays listed but shows « Inscriptions closes » and hides the button/iframe/mobile bar like `sold_out` — use `isBookable()`/`closedLabel()` rather than testing `sold_out`. All this lives in `supabase/functions/_shared/sync.ts`; the webhook also triggers an import when notified about an unknown form. Schema: `src/db/helloasso_ticketing.sql` (pasted manually, like every other `.sql` here — no `supabase/migrations/`).
- **Backend = Supabase Edge Functions, no PHP/extra server.** `sync-events` (run by a Supabase cron, `verify_jwt = false`, authenticated by an `x-sync-secret` header matching `SYNC_EVENTS_SECRET`; optional body `{"slug": ...}` to sync one event) pulls tier prices into `ticket_prices` and counts sold tickets into `tickets_sold` for every upcoming event with a slug, + `helloasso_synced_at`. HelloAsso API helpers (token cache, paginated GET, `countSoldTickets`) live in `supabase/functions/_shared/helloasso.ts`, shared with the webhook. Every HelloAsso call sends its own `User-Agent` (`USER_AGENT` in `_shared/helloasso.ts`): the **production** API's Cloudflare answers an HTML 403 page to the Edge Functions' default UA (it contains `SupabaseEdgeRuntime`) — the sandbox doesn't, so this only shows up in prod; a `HTTP 403 [cloudflare]` in sync errors means that. Don't add `/// <reference deno.ns="true" />` to new functions: `deno check` rejects it (`admin-create-user` still has it). `helloasso-webhook` receives HelloAsso notifications (Order/Payment/Form), authenticated by a `?secret=<HELLOASSO_WEBHOOK_SECRET>` query param (HelloAsso can't send custom headers, and doesn't sign payloads); it only reads the form slug from the payload — never stores or logs it, it contains payer data — and re-runs the same per-event sync as the cron (`syncEvent` in `supabase/functions/_shared/sync.ts`). Returns 500 on sync failure so HelloAsso retries. HelloAsso notifies ~3 s after an order, before the new item shows up in `/items` (observed in sandbox), so the webhook also re-syncs in the background at +10 s and +30 s via `EdgeRuntime.waitUntil`; the 15-min cron (`src/db/helloasso_cron.sql`, pg_cron + pg_net, secret in Supabase Vault) is the safety net. Both functions have `verify_jwt = false` in `supabase/config.toml`, like `admin-create-user`. To run one locally: `docker run --env-file <subset of .env.local + SUPABASE_URL> -v $PWD/supabase/functions:/f denoland/deno:2.1.4 deno run --allow-net --allow-env /f/<name>/index.ts` (needs the real `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` — not the publishable key).
- **The OAuth token is cached in `helloasso_token`** (singleton row `id = 1`): RLS enabled with no policies, so only the service role used by Edge Functions can read it, not even admins.
- **Capacity:** the HelloAsso API never exposes the form-level « Limiter le nombre total de participants » cap (checked on a published sandbox form, Nov 2026, and absent from the official OpenAPI spec), but `GET …/forms/{type}/{slug}/stats` gives each tier's `maxEntries`. `sync-events` writes the sum of the Registration tiers' limits into `helloasso_capacity` (NULL if any tier is unlimited). `ticket_capacity` is an optional admin override (for multi-tier events or a global-only cap); effective capacity = `COALESCE(ticket_capacity, helloasso_capacity)` — use `getCapacity()` from `src/lib/ticketing.ts` in the front, never `ticket_capacity` alone. `tickets_remaining` is a Postgres generated column built on that COALESCE — never write it, and it's absent from the `Insert`/`Update` types. LOOM's convention is **one single tier per event with its limit set on the tier** (that limit is both HelloAsso's real cap and the site's gauge) plus a promo code for the member discount; LOOM staff check after the fact, in the HelloAsso back-office export, that promo-code users were entitled to it.
- **Promo codes:** the API can't tell whether a promo code exists on a form (no field; `/discount-codes` is 403 for the org's API key), only that a sold item used one (`item.discount = { code, amount }`). So `ticket_member_discount` is an admin checkbox that shows a « tarif réduit adhérent avec code promo » line under the price, and `sync-events` counts promo-code sales into `tickets_sold_discounted` (counter only), shown in the admin event list as « N/capacity inscrits · dont M au tarif réduit ».
- **Counters only, no personal data:** never store participants' names, emails or order details in Supabase. `tickets_sold`/`tickets_sold_discounted`/`ticket_prices`/`helloasso_synced_at` are written only by the Edge Functions; the admin form (`pages/admin/Events.tsx`) edits `helloasso_form_slug` (accepts a pasted HelloAsso URL, normalized to the slug), `ticket_capacity` and `ticket_member_discount`, and nulls the synced columns when the slug changes, since they belonged to the previous form.
- **Front code:** all ticketing logic (form/widget URLs, availability thresholds, price/seat labels) lives in `src/lib/ticketing.ts`; Since the UX redesign (step 3): agenda cards are `components/agenda/AgendaEventCard.tsx` (button from `lib/eventCta.ts`, chips from `lib/eventChips.ts`), and `EventDetail` renders prices/seat gauge/sale end through `components/event/TicketInfo.tsx` (desktop sticky sidebar + mobile info block), the desktop-only `#billetterie` iframe section, and on mobile an in-flow « S'inscrire · dès X € » button opening HelloAsso in a new tab, plus a fixed bottom bar that only appears once that button has scrolled out of view (IntersectionObserver). `#billetterie` links scroll to the iframe on desktop and to `#inscription-mobile` on mobile. The old `EventCard`/`TicketAvailabilityBadge` are gone. Mockups are in `documents/maquette/`. The public HelloAsso URLs are built from `VITE_HELLOASSO_BASE_URL` (default `https://www.helloasso.com`, set it to `https://www.helloasso-sandbox.com` locally) and `VITE_HELLOASSO_ORG_SLUG` (default: the prod org slug), see `src/config.ts`.
- **UI:** paid event cards show a single « S'inscrire » button; `EventDetail` embeds the HelloAsso iframe on desktop, and on mobile shows a fixed bottom bar that opens HelloAsso full screen. Availability states: disponible / presque complet / complet.
- **Verified against the sandbox:** form tiers come as `tiers[].{label, price (cents), tierType}`; a paid ticket is an item with `type: Registration, state: Processed` (free tickets, `Registered`, not yet observed). Public form URL `/associations/<org>/evenements/<slug>`, iframe `…/widget`.
- **Credentials:** sandbox only during development (`helloasso-sandbox.com`, org `loom-test`), in the untracked `.env.local` and in `supabase secrets`: `HELLOASSO_API_URL`, `HELLOASSO_CLIENT_ID`, `HELLOASSO_CLIENT_SECRET`, `HELLOASSO_ORG_SLUG`, `SYNC_EVENTS_SECRET`, `HELLOASSO_WEBHOOK_SECRET`, `HELLOASSO_PUBLISH_MODE`, `HELLOASSO_IMPORT_CREATED_AFTER` (optional ISO date: only forms created on HelloAsso after it are auto-imported — set it to the go-live date in prod so pre-existing forms are ignored; unset = no filter; an unparsable value makes the import fail rather than import everything) — never with a `VITE_` prefix, which would ship them to the browser. Manual steps outside the code: registering the webhook URL in the HelloAsso back-office, enabling the cron in the Supabase dashboard, switching to production credentials later.

### Admin CMS pattern

**Admin shell (UX redesign step 9):** every admin page renders inside `components/admin/AdminLayout.tsx` (`title`, optional `actions` slot shown right of the title / in the mobile header): a 248 px grouped sidebar on `lg+` (Tableau de bord, Messages with an unread badge = `contact_tickets` with status `Nouveau`; Contenu; Association; Site; « Voir le site » + account menu), and below `lg` a fixed bottom tab bar (Accueil, Événements, Articles, Messages, Plus — « Plus » is a bottom sheet with the rest of the menu). The menu lives in the `NAV` array there. `/admin/navigation` (`pages/admin/Navigation.tsx`) edits the Boutique/Adhérer URLs and `show_shop_link`/`show_membership_link` (header + mobile menu hide those buttons when false, via `useExternalLinks()`). The admin SEO page was deleted (18/11/2026) once the sitemap became automatic. The dashboard (`pages/admin/Dashboard.tsx`, `/admin`) is built only from DB data: next 5 events (with HelloAsso sold/capacity), « À traiter » computed on the fly (upcoming drafts, HelloAsso sync older than 1 h, upcoming events without a recognised city or map, draft articles, partners without city), pending messages, last published articles, key figures; its « Créer » menu opens `/admin/events?nouveau=1` / `/admin/articles?nouveau=1`, which open the create dialog on arrival. « Visites du site » reads Cloudflare Web Analytics (the beacon in `index.html`; the site itself is NOT proxied by Cloudflare, DNS points straight at the VPS) and « Santé du site » reads UptimeRobot, both through the admin-only `site-stats` Edge Function (secrets `CF_API_TOKEN` with « Account Analytics: Read », `CF_ACCOUNT_ID`, optional `CF_SITE_TAG`, `UPTIMEROBOT_API_KEY`; a missing secret returns `{ configured: false }` and the card shows a hint), plus the upload server's admin-only `GET /upload/status` (`server/status.js`: disk, memory, origin certificate via TLS to 127.0.0.1:443, last build time + git commit). Hooks in `src/lib/siteStats.ts`; cards in `components/admin/dashboard/`. « Sécurité » (`SecurityCard.tsx`) shows the latest row of `security_audit_runs`: a nightly pg_cron job (`security-audit`, 5:00 UTC) calls the `security-audit` Edge Function (same `x-notify-secret` as `notify-new-message`; also callable by an admin via « Relancer l'audit »), which reads Auth's `disable_signup`, runs `public.security_audit_run()` (service role only: RLS off, anon write grants — new tables get them by default —, anon-executable SECURITY DEFINER functions, `protect_profile_is_admin` trigger, `banned_until = 'infinity'`, expected/failed cron jobs, plus a diff against `security_audit_baseline`: new admin, new auth user, policy or definer function added/changed/removed — each change reported once) and, for the nightly run only, e-mails **all** active admins when the status isn't `ok`. Migration `20261121100000_security_audit.sql` on `feature/supabase-docker`. When you add a cron job other code depends on, add it to `expected_jobs` there; a legitimate policy change will show up once as « à vérifier » the next night — that's intended. Supabase errors (`PostgrestError`) are not `Error` instances: wrap them (`new Error(error.message)`) before throwing into React Query, or the UI shows « [object Object] ». Primary admin buttons use `bg-primary` (brown), not the old `bg-orange-600`. Admin Messages (`pages/admin/Tickets.tsx`, route `/admin/tickets`) maps the CHECK-constrained `contact_tickets.status` values: `Nouveau` = unread (menu badge), `En attente` = read but still to handle (opening a message sets it), `Répondu`/`Fermé` = handled; tabs « À traiter / Traités / Tous » and the open message are in the URL (`?onglet=`, `?message=`). The old screen used `new/read/replied`, which the constraint rejected. New-message e-mails: each admin opts in with « Me prévenir par e-mail » in the Messages header (`components/admin/NotifyByEmailToggle.tsx`, `profiles.notify_on_message`); an AFTER INSERT trigger on `contact_tickets` (`src/db/message_notifications.sql`) calls the `notify-new-message` Edge Function through pg_net with an `x-notify-secret` header (secret in Vault as `notify_message_secret`, and `NOTIFY_MESSAGE_SECRET` in `supabase secrets`); the function re-reads the ticket by id and sends, via the association's Gmail (SMTP 465 with `nodemailer` — Supabase blocks ports 25/587 from Edge Functions; secrets `GMAIL_USER`, `GMAIL_APP_PASSWORD`), only the subject, the sender's name and a link to `/admin/tickets?message=<id>` — never the message body or the sender's e-mail. The trigger swallows errors so a notification failure can never block the contact form. Admin Events and Articles lists are row lists (no table): status tabs in `?onglet=` (Events: upcoming/past/drafts grouped by month; Articles: all/published/drafts + category filter, 20 per page), click on a row = edit, ⋯ menu = Modifier / Dupliquer (opens the create dialog pre-filled, as a draft) / Voir sur le site / Publier–Mettre en brouillon / Supprimer. Admin Galerie (`pages/admin/Gallery.tsx`): albums column on `lg+` / a native `<select>` + « Nouvel album » button below (photo counts from the upload server's `image_count`), inline drop zone (no upload dialog) that uploads into the album on screen, album ⋯ menu = delete. No album is opened by default (Florent's choice, 21/11/2026): with no `?albumId=` (or an unknown one) the page shows « Aucun album choisi » and import is disabled — never upload into a default album behind the admin's back. A new album opens right after creation; its name goes through `cleanAlbumName()` (trims spaces — a trailing space once created an invisible duplicate — and replaces `/` `\`, which the server's `path.basename` would otherwise cut: « Soirée 21/11/2026 » became album « 2026 ») and case-insensitive duplicates are refused. Gotcha: an `sr-only` span inside an `overflow-x-auto` list must have a `relative` ancestor inside the list, or its absolute box escapes the scroller and widens the whole page on mobile. Admin Partenaires is a card grid sorted by name (category chips with counts, search over name/type/city/benefit, 12 cards then « Voir les N autres »), flagging « Ville à renseigner » when `city` is empty since the public city filter depends on it.

Every admin resource page (`pages/admin/Articles.tsx`, `Events.tsx`, `Partners.tsx`, ...) follows the same shape: a table with search, a shadcn `Dialog` reused for both create and edit (toggled via an `isCreating` flag), and a separate delete-confirmation `Dialog`. Long-form content (article body, event description) is edited with `@uiw/react-md-editor` (`MDEditor`) and stored as raw Markdown. `src/components/ui/dialog.tsx`'s `Dialog` wrapper has a workaround effect that force-releases Radix's scroll lock shortly after `open` becomes `false` — heavy children like `MDEditor` can otherwise leave `document.body` permanently `overflow: hidden` after the dialog closes.

`src/pages/admin/HomeSettings.tsx` edits a singleton `site_settings` row (`id = 1`, enforced by a `CHECK` constraint) that drives the homepage hero image/link and the navbar's external links (Boutique/Adhésion) — consumed via `useQuery(['siteSettings'], ...)` in `Navbar.tsx`, `Index.tsx`, and `SettingsRedirect.tsx` (used for the `/shop` and `/membership` redirect routes). `hero_image_width`/`hero_image_height` are captured automatically by `ImageUpload.tsx` (reads `naturalWidth`/`naturalHeight` off the uploaded file) whenever the hero image is set in `HomeSettings.tsx`; `Index.tsx` uses them to reserve the hero image's aspect ratio via inline `style={{ aspectRatio }}` before it loads, avoiding layout shift (CLS) — rows saved before this field existed just render without a reserved ratio until re-saved from the admin.

### Markdown rendering

Content authored via `MDEditor` is rendered on public detail pages (`ArticleDetail.tsx`, `EventDetail.tsx`) with `react-markdown` + `remark-gfm` inside a Tailwind Typography `prose` wrapper — the `@tailwindcss/typography` plugin must stay registered in `tailwind.config.ts`'s `plugins` array, or `prose` classes silently do nothing (Tailwind's base reset strips all default heading/list/quote styling otherwise). Card/preview components (`EventCard.tsx`) must not render the raw Markdown string directly — use `stripMarkdown()` from `src/lib/markdown.ts` to get plain text for excerpts, SEO meta descriptions, and structured data.

### SEO

`useSEO` (`src/hooks/useSEO.ts`) plus `SEOPage.tsx`/`InternalLinks.tsx`/`SEOStructuredData.tsx` components handle per-page meta tags, Open Graph/Twitter cards, and JSON-LD. `scripts/generate-seo.js` runs as `postbuild` and writes `dist/sitemap.xml` — never `public/`: the server builds inside the git checkout, and a tracked file rewritten on every build would block the next `git pull`. It lists the static pages, published articles/events (read with the anon key from `VITE_SUPABASE_*`, loaded from the env or `.env*` files) and non-empty public albums from the upload server; any source that fails is skipped with a warning, so it never fails the build. `public/robots.txt` is static and points to `/sitemap.xml`; the base URL is `https://lgbt-loom.fr`.

### Slugs and redirects (UX redesign step 10)

`slugify()` in `src/lib/slug.ts` transliterates accents (« Nîmes » → `nimes`; the old admin rule dropped accented letters, giving `nmes`, `f-te`, trailing `-`) and must stay identical to the SQL `public.slugify()` in `src/db/slug_redirects.sql`. The admin forms only derive the slug from the title while creating or while the item is unpublished; a manually typed slug is normalised on blur. Every slug change on `events`/`articles` is recorded by the `record_slug_redirect` trigger into `slug_redirects (kind, old_slug, new_slug)` (chains collapsed, a revived slug drops its redirect), whoever makes the change; `EventDetail`/`ArticleDetail` look it up via `useSlugRedirect()` when the slug isn't found and `navigate(..., { replace: true })` to the new address, else 404. These are client-side redirects (the SPA has no server-side 301s); a generated NGINX map could add real 301s later.

### Path alias

`@/*` maps to `src/*` (configured in `vite.config.ts` and `tsconfig.json`).

## Deployment

The upload server (`server/upload.js`) runs separately from the main frontend (`upload.lgbt-loom.fr` in prod) — it must be deployed/restarted independently when changed. When a change touches both (e.g. the upload auth), deploy the front first, then the server: an old front talking to a new server loses uploads, the reverse is harmless.
